# ADR-0038 性能复查：补全分项计时、游戏内测量、按热点优化（M21）

- 状态：已采纳
- 日期：2026-10-31
- 相关：ADR-0019（Alpha 的性能预算和分项计时）、ADR-0036、ADR-0037（M20 的设备）

## 背景

- 用户 2026-10-31 要求继续开发，"要注意性能问题，但是又要获得最佳表现"，最后做 review 和修复，直到找不出问题。
- 上一次按预算量性能是 M9（ADR-0019，2026-10-20）：主世界 5,000 段传送带、500 台设备，加三颗星球，本模组每刻 1.16 ms（预算 10 ms）。之后加了 M10–M20 十一个里程碑的内容（机甲、舰队、黑雾、聚落、钓鱼、深空、化学和生物……），一直没再按这个规模量过。
- 分项计时（`/universe perf`）有 15 个全局 tick 和 3 种方块实体没计进去：黑雾的基地、巢穴、航线、护盾和枪骑，深空和残骸，全息信标，控制面板，传送门，重力线圈，守卫机塔，载具召唤台，建造无人机，雷击石；捕鱼笼、间歇泉、生物蛋。
- 量性能要开客户端、进存档、敲命令，本机以外（CI、云端的会话）做不了。
- 这次的会话在云端的容器里跑，有 4 个核，没有显卡；容器里有 Xvfb 和 Mesa 的软件渲染。

## 决定

### 一、量

- 上面那些全局 tick 和方块实体都补上分项计时。方块实体的 ticker 用 `ServerPerf.timed(type, ticker)` 包一层，分项名按类型（`block/<id>`）。
- 参照基地加第三个参数：`/universe bench <传送带> <设备> [化工设备]`。化工设备是化学反应釜（合成氨、铁催化剂）和生物反应器（产甲烷菌）一台隔一台，排在环线后面，每排前面一行人造恒星和感应塔；每秒补满原料、清掉产物。反应釜要做合成氨，搭的时候把它记成全服已发现，所以只在测试世界里用。
- 游戏内测量：`./gradlew runGameTestServer -PperfBench=<传送带>,<设备>,<化工设备>,<刻数>` 时，测试服务端只登记一个测试：在测试场地以东 4,000 格搭参照基地，按真实时间等区块更新起来，热身 400 刻，再分项计时给定的刻数，报告写进日志（`Perf:` 开头）。不用开客户端、不用同意 EULA，CI 和云端都能跑。测试服务端两刻之间不等，量的是每刻的耗时，不是 TPS。

### 二、改

只改量出来的或者读代码核实过的热点；每一处都要做到玩法结果不变、画面不变。三个只读的代理分别扫了方块实体、全局和玩家 tick、客户端每帧的路径，清单逐条核实以后再改。

服务端：

- 化学反应釜每刻都重新解一次平衡转化率（二分 100 次，每次几个对数）。按（反应、工况、催化剂对不对、气温）记下上一次的结果，几样都没变时直接用。按名字找物品、催化剂、配方 ID 的地方都记下来。
- 设备每刻调 `setChanged()`：除了标记区块要存盘，还要挨个通知六个邻居（给比较器用）。比较器读的是物品栏装了多少，进度走一刻读数不变，所以只改了进度时只标记存盘（`MachineBlockEntity.markUnsaved()`），物品栏真变了的那一刻再 `setChanged()`。配方设备基类、反应釜、大气提取器、释放塔、生态播种站、水培槽、微生物设备、采油机、蛋序列器、生物蛋都改了。
- 配方设备基类每刻为检查产物格新建一份产物、反查注册表判断能不能增产：按配方记下（`MachineRecipe.prototype`、`productive`）。
- 发射井每刻都问"还有没有能建的"，球建满以后每问一次都要把每层最多 512 个节点、1,536 条框架扫一遍。`DysonLayer` 加一个计数，结构点、预定、网格每变一次加一，`nextTarget` 按（计数、纬度限制）记下上一次的结果。
- 炮塔没有目标时每 4 刻在几十格（等离子炮塔 193 格见方）的范围里找一遍 Mob。新加 `LoadedEnemies`：按实体进出维度的事件记下每个维度加载着的黑雾，一个都没有时跳过查找（原来找出来也是空的）。舰队单位找黑雾也一样。导弹炮塔为每个候选算一遍同电网的信号塔，改成一刻算一次。
- 机甲的三门武器每刻各查一次附近的实体：改成一刻按最远的射程查一次，每门再按自己的射程挑。查询只按类型筛，敌意、死活每门照旧重新判断，挑出来的目标和原来一样。
- 维度键解析成恒星系、天体、货船编号都用正则：太空、星球、货船三处按维度键记下结果（维度键是驻留的，结果不会变）。设备每刻、玩家每刻、客户端每帧都在用。
- 零碎的：生物反应器从配方 ID 推工艺、大气提取器每刻给气体排序、水培槽线性找植物、外骨骼的超频格、统计每秒拼设备名，都改成算一次记下。

客户端：

- 传送带上的物品：原来每帧每个物品都新建渲染状态、解析一次模型；每段传送带还从线路最前面扫起，一条满载的长线每帧要扫上万次。改成每帧每条线路只算一次各物品的位置，每段用二分找到自己那一截；同一种货物一帧只解析一次模型（`SharedItemModels`）。只有模型树里全是固定模型、也不带附魔光效和动画贴图时才共用：用 `TrackingItemStackRenderState` 记下解析时用到的模型，里面有按种子、时间、组件挑子模型的（比如没有目标、按种子乱转的指南针）就照旧逐个按自己的种子解析。帧号用 `RenderFrameEvent.Pre` 数（`RenderFrames`）。
- 护盾穹顶：每个顶点十来次三角函数、两个 `Vec3`，近处一个穹顶每帧约 4,600 个顶点。顶点都落在固定的几组经纬上，按组预先算好三角函数；随时间流动的波纹用和角公式拆开，每帧只算 4 次三角函数。表里的数和逐个现算的逐位相同，波纹只差浮点舍入。
- 物流无人机、运输船、建造无人机、配送机器人：每帧每架解析一次模型，改成每种一帧解析一次（同样用 `SharedItemModels`）。
- 拿着蓝图时的预览：每帧把最多 4,096 格重新转一遍、查一遍邻居，每格还查一次实体碰撞。摆法（蓝图、位置、转向、只贴设备）不变时复用转好的格子和遮挡面，格子的顺序和原来一样；"有没有实体挡着"一刻查一次（实体的碰撞箱每刻才动）。
- 工地虚影：先按整个工地的包围盒做视锥和距离剔除，再逐格剔除视野外的。视野外的格子不再占"最多画 6,000 格"的名额。
- 牵引光束：附近的船每刻查一次（多查 16 格，摄像机挪出这么远就重查），每帧再按摄像机的位置筛。

### 三、没改的

- 停在星球上的飞船每刻对整个船体做一次落地探测，大船（上千格）可能到半毫秒。改法要动碰撞，碰撞形状伸出本格的方块（推动中的活塞）得单独处理，这次不动，记下来以后做。
- HUD 面板每帧重建文字、全息信标每帧遍历全部信标、外星动物躲捕食者的查询、驾驶飞船时的辅助瞄准：都是几十微秒以内，或者只在少见的情况下才有，没改。

## 结果

2026-10-31 实现。

- 参照基地 `-PperfBench=5000,500,100,1200`（5,000 段传送带、500 台一型制造台和分拣器、50 台化学反应釜和 50 台生物反应器，量 1,200 刻，云端容器 4 核）：

  | 项 | 优化前 | 只改反应釜后 | 全部改完 |
  |---|---|---|---|
  | 服务器每刻 | 1.63 ms | 1.57 ms | 1.18 ms |
  | 本模组合计 | 1.29 ms | 1.13 ms | 0.79 ms |
  | 一型制造台（500 台） | 0.394 ms | 0.410 ms | 0.152 ms |
  | 化学反应釜（50 台） | 0.340 ms | 0.094 ms | 0.038 ms |
  | 生物反应器（50 台） | 0.048 ms | 0.056 ms | 0.032 ms |
  | 分拣器（500 个，没改） | 0.319 ms | 0.359 ms | 0.352 ms |
  | 电网 | 0.114 ms | 0.117 ms | 0.124 ms |

  同一项在几次之间差一成左右是测量的波动（分拣器、电网都没改）。反应釜每台每刻从 6.8 µs 降到 0.8 µs，制造台从 0.79 µs 降到 0.30 µs。和 M9 的 1.16 ms 不是同一台机器、也不是同一个规模，不能直接比。
- 单元测试 1,190 个（新加三个：戴森球层的建造目标跟着预定、建成、读档、拆除、纬度限制重新找；`-PperfBench` 的参数），游戏内测试 219 个全过。
- 最后的 review 一共两轮。第一轮找出并修掉的：`LoadedEnemies` 在区块暂时降到看不见时会把还在维度里的黑雾拿掉，区块回来时又没有加入事件补上，炮塔会对它们视而不见（改成只在实体真的移除时拿掉）；传送带按（世界、刻、插值）认帧，同一毫秒的两帧或冻结时间时会用到旧的位置表（改用帧号）；共用模型让没有目标的指南针都指一个方向（改成只共用固定模型）；退出世界后静态缓存还拿着上一个世界；`-PperfBench` 写错时测试服务端启动就崩、没有提示；几处计时包装没用上 `ServerPerf.timed`；Javadoc 放错了位置。没采纳的：把九处"物品栏变了才 `setChanged`"收成一个基类方法，每处得多一个布尔变量，并不更清楚。
- 客户端没能在容器里无头验收：Xvfb 的 GLX 没有 sRGB 帧缓冲，Minecraft 26.3 的 OpenGL 后端（SDL3）要求 `FRAMEBUFFER_SRGB_CAPABLE`，建不了窗口；装上 Mesa 的 EGL、用 SDL 的 offscreen 驱动能起来、读完资源，但打开测试服务端的世界以后停住，看不到画面。客户端的改动只有编译和逐行核对把关，留给作者在本机用开发脚本看一遍：传送带上的物品、护盾穹顶、物流和建造无人机、拿着蓝图的预览、工地虚影、牵引光束。

## 理由

- 测量放进 GameTest：每次改完都能在任何机器上按同一个规模量，对比前后。M9 的做法要开客户端，只能在作者本机做。
- 优化只做缓存纯函数的结果、提前返回、少通知邻居：都不改变玩法的数，也不改变画面，GameTest 照旧全过就说明行为没变。
- 不降画质：用户要的是"最佳表现"，所以客户端只省重复的计算，不减顶点、不缩视距、不加画质选项。

## 后果

- 新代码多了几处缓存，缓存失效的条件写在各自的注释里；改那几处的数据（戴森球的层、反应釜的工况、蓝图的摆法）时要记得缓存跟着失效。`DysonLayer` 的计数由单元测试覆盖。
- `/universe bench` 的化工设备会把合成氨记成已发现。
- `-PperfBench` 时测试服务端只跑测量，不跑别的游戏内测试；CI 照旧不带这个参数。

## 备选方案

- 用 Spark 剖析：要装模组、开客户端，结果是方法栈，不对应子系统；分项计时加 GameTest 更直接，也能重复。
- 给客户端加"性能模式"（少画几层戴森球、缩短护盾和虚影的视距）：用户要最佳表现，不降画质。
- 炮塔按位置错开找目标的刻：会改变发现目标的时机，不采用。
