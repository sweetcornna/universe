# ADR-0019 Alpha：性能、兼容、多人和发布

- 状态：已采纳（M9 已实现；上传发布由作者操作）
- 日期：2026-10-20

## 背景

- 路线图的 M9：性能优化，兼容性测试（Sodium、Iris、JEI、Jade），多人测试，发布页、截图和文档，在 Modrinth 和 CurseForge 发布 Alpha。退出标准是公开发布 0.7 Alpha。
- 技术架构 §5 的性能预算：中等规模的基地（5,000 段传送带、500 台设备、同时加载 3 颗星球）保持 20 TPS，本模组每刻耗时低于 10 ms；完整显示戴森球时，中端显卡 1080p 帧率下降不超过 10%；第一次去一颗星球（含创建维度）等待不到 5 秒。
- 现状：
  - 没有自己的性能统计。传送带有一个核心层的基准（`BeltTest`，1 万段），设备、电网、物流、戴森球都没有在游戏里量过；也没有能一键搭出大基地的工具。
  - 没写过 GameTest。专用服务器从没启动过：`runServer` 要先同意 EULA，这得由作者本人决定。只在客户端用的代码有没有漏进公共代码，现在只靠写代码时注意。
  - 多人只在单人世界里验过，同步的包都是给一个玩家看的。
  - 兼容模组在 Modrinth 上都有 26.3 的 NeoForge 版本（2026-10-20 查）：JEI 31.16.0.86（测试版，maven.blamejared.com 上有 API 包），Jade 26.3.5，Sodium 0.9.2，Iris 1.11.7（要 Sodium）。REI 也有 26.3 的版本，EMI、WTHIT 没有。作者同意把这四个作为开发依赖下载。
  - `mod_version` 还是 0.1.0，`neoforge.mods.toml` 的描述是立项时写的。

## 决定

### 性能

- 自带分项计时：`/universe perf start` 开始记录，`/universe perf report` 列出每一项平均每刻多少毫秒和占服务器一刻的比例，`stop` 停止。不记录时只多一次布尔判断。分项是传送带、电网、物流、戴森球、各类设备（按方块实体类型分）、分拣器、海盗、小行星、蓝图放置、玩家每刻的处理（生存、外骨骼、兴趣点、守卫机、任务、驯养）。统计和排序放在核心层，有单元测试。
- 不依赖 Spark：分项计时只看本模组，Spark 看全局时作者自己装。
- 基准基地：`/universe bench <传送带段数> <设备台数>` 在玩家附近的空地上搭一片工厂：一圈圈装满物品的环形传送带，一排排在干活的制造台，用人造恒星和电力感应塔供电。搭好以后跑 `perf` 量。按预算的规模（5,000 段、500 台）量一次，再加上去两颗星球的情形。
- 优化按量出来的热点做，不预先改。目标就是 §5 的预算。

### 兼容

- JEI：写插件。每种设备配方一个分类（冶炼、制造、精炼、化工、粒子对撞），列出原料、产物、秒数和能做的设备；研究解锁的配方照样显示，界面上注明要哪个科技。工作台配方 JEI 本来就会显示。设备界面里点配方的箭头打开对应分类。
- Jade：写服务端数据提供者。设备显示进度、在做什么、缺电还是缺料；采矿机显示每分钟产量和剩余储量；发电设备显示功率；物流站显示每格的物品；射线接收站显示效率。
- 兼容代码放在 `compat` 包，对方模组存在时才加载，编译时只依赖对方的 API 包，发布的 jar 里不带它们。
- Sodium、Iris：不写代码依赖，只装上测。用 Gradle 属性 `-Pcompat=sodium`、`-Pcompat=iris` 决定开发客户端装不装，平时不装，免得影响别的无头验收。重点看自己画的东西：星球天空、戴森球、飞船和设备的模型、传送带上的物品、HUD。坏了再修。

### 多人

- 专用服务器：用 `gameTestServer` 启动（它跑完测试就退出，不走 EULA 流程；要是也要求同意 EULA，停下来问作者）。写几个 GameTest：制造台出产物、传送带送东西、电网分电、研究站加点。服务器能启动、测试能过，就说明公共代码没有引用客户端的类。
- 两个客户端：加一个运行配置 `client2`，游戏目录是 `run2`，用户名不同。第一个客户端用 `/publish` 开局域网，第二个直接连进来，两边都无头。看同步：别人放的设备和传送带、开飞船、戴森球、研究进度、交易、剧情广播、蓝图预览。

### 发布

- 版本号改成 0.7.0-alpha，`neoforge.mods.toml` 写上正式的描述、主页和问题反馈的地址、图标。
- 准备 Modrinth 和 CurseForge 的页面文字（中英文）、截图和更新日志，放在 `docs/release/`。上传要用作者的账号，由作者自己操作。
- 剧情文字还是占位，Alpha 的说明里写明。

## 理由

- 分项计时比 Spark 更合用：Spark 给的是方法栈，要从里面认出哪段是传送带；分项计时直接对应设计里的子系统，而且以后每次加功能都能拿基准基地复查。
- 基准基地用命令搭，不存一个测试存档：存档跟着版本和存档格式走，升级以后就打不开了；命令每次按当前的代码搭。
- JEI 是装的人最多的配方查看模组，REI 的玩家少得多；方块信息模组在 26.3 上只有 Jade。
- `gameTestServer` 能在不碰 EULA 的情况下验证专用服务器，GameTest 以后也能放进 CI。

## 结果

2026-10-20 实现。和上面的决定不同或决定里没写的：

### 性能

- 第一次量（优化前）：主世界参照基地 5,000 段传送带、500 台设备，30 秒，服务器每刻 6.78 ms，本模组 1.64 ms。分拣器占 1.167 ms（500 个，每个 2.3 µs），制造台 0.190，电网 0.165，传送带 0.014。
- 分拣器慢在两处：`BeltLine` 从线路最前面逐个往后找取货窗口，`indexFor` 从后往前线性找插入位置；前面的设备原料满了，分拣器每刻对每个候选物品模拟一次插入。改成二分查找（`firstBelow`）；一次抓取里同一种物品只问一次能不能放，前面的容器拒收时 4 刻后再试（只对容器，往传送带上放不退避）。`BeltTest` 加了一条长线路上和线性扫描对照的随机测试。
- 参照测量：主世界 5,000/500，加三颗星球（s5/p2、s6/p1、s7/p2）各 1,000 段、100 台，全部强制加载，另有存档里已加载的 s1/p1 和 s0 太空，量 60 秒：服务器每刻 6.25 ms，本模组 1.16 ms（19%）。分拣器 0.367（801 个），制造台 0.324（800 台），电网 0.263（5 个维度），外星生物 0.11，传送带 0.021（4 个维度、8,000 段），参照基地的补给 0.015。800 台都在干活，主世界每分钟 21,750 个齿轮。预算是 10 ms。
- 第一次去一颗星球：建维度 4 ms，从敲命令到落地约 2 秒（预算 5 秒）。
- 戴森球天空（s0 太空离恒星 6,000 格，1600×900，不限帧）：优化前四层壳建满 525 fps，每帧 CPU 1.27 ms、4.8 万个顶点；上限（10 层壳加 18 条轨道各 2 万张帆）160 fps，5.4 ms，16.4 万个顶点。原因是每帧都重算全部顶点再上传。改成每刻算一次（同一刻里后面几帧画上次上传的缓冲），相机挪动 4 格以上也重算。优化后四层壳 1,550 fps（每帧多 0.07 ms），上限 1,130 fps（多 0.32 ms）。折算到 60 fps：四层壳约多 2.5%，上限约多 10%。
- 画质设置（`config/universe-client.toml`，模组列表里的"配置"按钮）：完整、简化、不显示。简化时球壳不细分，背面的框架和节点不画，帆最多画 200 个点；上限场景简化后约多 4%。

### 兼容

- JEI 用 31.16.0.86（26.3 上还是测试版）。它的运行库 `net.mezzdev.config:mezz_config` 也在 JEI 的仓库里，Gradle 的仓库过滤要放行这个组。
- JEI 的说明页只在空格处换行，中文会在"1%"这种数字两边断开、词中间加连字符。说明文字先按本模组的 `TextWrap` 断好，一行一个组件交给 JEI。配方分类里英文的"需要研究"一行太长，放不下时截断加省略号，鼠标指着时提示全文；英文键改成更短的"Research: %s"。
- Jade 显示的数据由服务端每次查看时写进去：设备的数据数组、在做的配方的第一个产物、射线接收站的效率、物流站每格的物品。
- Sodium 0.9.2 在 NeoForge 26.3.0.86 和 26.3.0.95 上都启动就崩溃：它的 mixin 找的是 4 个参数的 `extractVisibleBlockEntities(Camera, float, LevelRenderState, Frustum)`，现在的 NeoForge 里没有这个签名，和本模组无关。0.9.3-beta.1 去掉了这个 mixin，更新说明写的是适配 NeoForge 26.3.0.65 以后的构建。作者同意下载以后，`sodium_version` 改成了它。
- Sodium 0.9.3-beta.1：启动正常，本模组自己画的东西都对：设备模型、传送带上的物品、飞船（实体和飞行 HUD）、星球地形和天空、生存模式的 HUD、戴森球（两层壳加一条帆轨道，约 2.6 万个顶点，每帧 0.009 ms）。日志里没有本模组的警告。
- Iris 1.11.7：Modrinth 上标的是配 Sodium 0.9.2，它自己的 `neoforge.mods.toml` 只要求 Sodium 0.6 以上，配 0.9.3-beta.1 能加载。不装光影包时，上面几样和只装 Sodium 时一样，帧数也差不多。
- Iris 的 `neoforge.mods.toml` 还在用 `logoFile`，NeoForge 启动时会停在"模组加载警告"界面，玩家点"继续"就行，但开发脚本的直接进世界会被它挡住。无头测试时在开发目录的 `config/neoforge-client.toml` 里临时关掉 `showLoadWarnings`，测完改回来。
- 光影包用 Complementary Reimagined r5.9.3 测（作者同意从 Modrinth 下载，只放在开发目录的 `run/shaderpacks`，不打包、不提交）。
- 开发客户端里一开光影包，第一帧就崩在 Iris 的阴影渲染里。原版的渲染管线把顶点格式补成 16 格，Iris 给光影包建的管线只有 1 格，开发环境才开的渲染校验（`IS_RUNNING_IN_IDE`）逐格检查时越界。玩家的游戏里没有这层校验，所以 `build.gradle` 在装 Iris 时给开发客户端加上 `-Dneoforge.disableBlaze3DValidation=true`，和玩家的环境一样。
- 关掉校验以后能正常玩：设备、传送带上的物品、飞船、HUD 都正常，有光影效果；星球地形正常，毒雾星球的雾色、宜居星球的天色光影包都接上了，宜居星球天上的另一颗行星也看得见。
- 光影包的 `dimension.properties` 把不认识的维度都当主世界（`dimension.world0=*`），本模组的星球和太空维度用的都是光影包自己算的主世界天空。太空里也是蓝天白云，星空看不见。这得光影包那边支持，本模组改不了，没修。
- 戴森球原来在主世界和太空都看不见，顶点照常生成，现在修好了。它原来在天空画完以后（`RenderLevelStageEvent.AfterSky`）自己开一个 RenderPass 画，新开的 RenderPass 绑的是原版的主帧缓冲。开着光影包时，原版天空的几条管线被 Iris 换成光影包的程序，画进光影包自己的缓冲区；光影包最后一步把整个画面写回主帧缓冲，先画在那里的戴森球就被盖掉了。本模组的 5 条天空管线（星空、恒星、行星、戴森球的发光和球壳）Iris 不认识，日志里报 "Missing program ... in override list"，按原样画，画进当时绑着的缓冲区。星球天空渲染器画的行星和光影包接管的天空在同一个 RenderPass 里，跟着进了光影包的缓冲区，所以一直看得见。
- 改法：戴森球不再自己开 RenderPass，画在天空的 RenderPass 里，排在最后。本模组的维度由星球天空渲染器画完天空后调用；主世界用原版天空，由 mixin 接在 `SkyRenderer.renderSunMoonAndStars` 的末尾。RenderPass 开着的时候不能往缓冲区里写，顶点改在提取阶段上传。
- 复测：Complementary Reimagined 下，主世界的白天和日出、母星系的太空、母星的卫星上都看得见戴森球。不装 Iris、装 Iris 不开光影包也各跑了一遍，画出来和改之前一样，开发环境的渲染校验没报错。
- M9 当中 NeoForge 从 26.3.0.86 升到 26.3.0.95（见 ADR-0001 的升级记录），代码不用改。

### 专用服务器和 GameTest

- `gameTestServer` 确实不走 EULA。4 个测试：通电的制造台做出齿轮；没接电的制造台停在"缺电"，不出东西、原料不动（和上一个一起代替了"电网分电"）；一排传送带把铁锭送进尽头的储物仓；研究站接上电、放进电磁矩阵后给当前研究攒点数。连 NeoForge 自带的一个，5 个全过。
- 场地是 7×4×7、底下一层平滑石的结构（`data/universe/structure/gametest/platform.nbt`，由 `tools/gametest_platform.py` 生成）。原版的 `minecraft:empty` 只有 1×1×1。
- 测试函数和测试只在 NeoForge 打开游戏内测试时注册（开发环境），正式版里没有这些注册表条目。
- 传送带网络在放下方块的下一刻才把新的几格连成线，测试里隔两刻再往上放东西。

### 多人

- 第二个客户端 `runClient2`：游戏目录 `run2`，用户名 Dev2，`-PjoinServer=localhost:<端口>` 启动后直接连。两个都无头：开发脚本加了 `lan <端口>`（对局域网开放、给客人命令权限、不验证正版账号）和 `waitplayers <人数>`（等在线人数变成这个数）。
- 原版对局域网开放时监听所有网卡，第一次这样做 Windows 防火墙会弹窗。开发脚本运行时由 `IntegratedServerMixin` 改成只监听回环地址，不弹窗。内置服务器默认验证正版账号，离线的开发客户端连不进来，主机先关掉验证。
- 验证过的：客人看到主机搭的设备和传送带上走的物品，打开设备界面看到服务端的功率、进度和产物；科技树和研究进度同步；客人去两颗没人去过的星球（运行时新建维度）能进、地形和天空正常；主机拼船、开炮、飞走，客人在旁边看得到；主机建的戴森球画在客人的天上；客人在空间站卖东西，信用点各算各的。蓝图预览只在拿着蓝图的人的客户端上画，没测。
- 修了一个问题：剧情节点是整个世界的，玩家上线时补上不在线时到达的节点进度，补的时候原版照样往聊天栏里报，刚进服的人会当着所有人"完成了挑战：任务完成"。现在补进度时临时关掉进度播报（游戏规则 `SHOW_ADVANCEMENT_MESSAGES`，在服务器线程上一口气做完马上还原），进度照样补上。
- 测多人时还发现：`neoforge.mods.toml` 用 `logoFile` 会让 NeoForge 26.3 启动时弹"模组加载警告"界面，第二个客户端卡在那里连不上服务器。改用 `iconFile`。

## 后果

- 多两个可选的编译依赖（JEI API、Jade）。版本更新时，它们和 NeoForge 一起跟进；它们没出新版本时，兼容代码先关掉，不挡升级。
- 基准基地会在世界里放几万个方块，只给有权限的人用，最好在测试世界里用。
- 发布要作者的账号，最后一步不能自动完成。
- 开光影包时本模组的维度用的是光影包的主世界天空，太空里看不见星空。Alpha 先这样发，已知问题里写明。
- 主世界的戴森球靠 mixin 接在原版 `SkyRenderer.renderSunMoonAndStars` 上，升级 Minecraft 时要核对这个方法。签名变了启动时就会报错（`defaultRequire` 是 1），不会悄悄不画。

## 备选方案

- 用 Spark 的 API 做统计：多一个依赖，而且 Spark 本身不一定先出 26.x 的版本。
- 同时做 REI 的插件：REI 有 26.3 的版本，但用户少，等有人要再做；EMI 没有 26.3 的版本。
- 用 `runServer` 测专用服务器：要先同意 EULA，那得作者本人决定；`gameTestServer` 已经够用。
- 光影包下的戴森球用 `IrisApi.assignPipeline` 把管线指给光影包的某个程序：光影包的程序按自己的算法重算颜色（天空程序直接换成它的天色，自定义天空的颜色会被平方），戴森球的颜色保不住，还要多一个 Iris 的编译期依赖。画进天空的 RenderPass 不依赖 Iris，颜色也不变。
